# Architecture Documentation — Snack Overflow

## 1. System Overview

Snack Overflow is architected as a decoupled, full-stack web application designed for high performance, maintainability, and horizontal scalability:

```text
┌─────────────────────────┐          ┌───────────────────────────┐
│     Frontend Client     │  HTTP    │      Backend Server       │
│  React + Vite + TS      ├─────────►│  Express + Node.js + TS   │
│  (Runtime Configurable) │◄─────────┤                           │
│                         │    WS    │  • JWT Auth & RBAC        │
│                         │◄═════════╡  • Error & Log Handling   │
│                         │          │  • WebSocket Server       │
└─────────────────────────┘          └─────────────┬─────────────┘
                                                   │ Prisma ORM
                                                   ▼
                                     ┌───────────────────────────┐
                                     │    PostgreSQL Database    │
                                     │        (Railway)          │
                                     └───────────────────────────┘
```

## 2. Frontend Architecture

### 2.1 Runtime Configuration Pattern
To support zero-downtime, continuous deployment across multiple environments (local development, staging, production on Railway) without rebuilding JavaScript bundles, Snack Overflow uses a **runtime configuration pattern**:

- **Execution Flow**:
  1. `index.html` loads `<script src="/config.js"></script>` before the bundle execution.
  2. `/config.js` sets `window.__APP_CONFIG__ = { API_BASE_URL: "...", WS_URL: "..." }`.
  3. `src/config/env.ts` reads `window.__APP_CONFIG__` first. If absent, it falls back to Vite build-time environment variables (`import.meta.env.VITE_API_BASE_URL`).
  4. In Docker / cloud deployments, the `/config.js` file can be replaced or mounted as a config map or generated by an entrypoint script from environment variables without recompiling TypeScript or rebuilding Vite assets.
- **Security Rule**: The frontend runtime config only contains public endpoints (`API_BASE_URL`, `WS_URL`). It **never** contains secrets, database credentials, or private keys.

### 2.2 Centralized API Client
- Built on standard `fetch` with TypeScript generics.
- Automatically injects JWT Bearer tokens from client storage when present.
- Normalizes API responses into standard `ApiResponse<T>` envelopes.

## 3. Backend Architecture

### 3.1 Layered Architecture
The backend follows strict separation of concerns:
- **Routes (`src/routes/`)**: Map URL endpoints and HTTP verbs to middlewares and controllers.
- **Controllers (`src/controllers/`)**: Handle HTTP request extraction, status codes, and call services.
- **Services (`src/services/`)**: Encapsulate domain and business logic, interact with Prisma ORM.
- **Middlewares (`src/middleware/`)**: Reusable request interceptors for logging, authentication, authorization, and validation.
- **Config & Database (`src/config/`)**: Environment validation and Prisma singleton instance.
- **WebSocket (`src/websocket/`)**: Real-time connection management and event broadcasting.

### 3.2 Standardized API Responses
Every API endpoint returns a predictable JSON structure:

```json
{
  "success": true,
  "message": "Optional human-readable message",
  "data": { ... },
  "timestamp": "2026-11-22T09:00:00.000Z"
}
```

Error response:
```json
{
  "success": false,
  "message": "Descriptive error message",
  "error": {
    "code": "ERROR_CODE",
    "details": null
  },
  "timestamp": "2026-11-22T09:00:00.000Z"
}
```

### 3.3 Security & Authentication Foundation
- **JWT**: Tokens generated using HMAC SHA-256 (`jsonwebtoken`) signed with `JWT_SECRET`.
- **Password Storage**: Passwords hashed using `bcrypt` with 10 salt rounds. Plaintext passwords are never stored or logged.
- **RBAC**: Role-based access control middleware distinguishes between `ADMIN` (inventory restock, management) and `MEMBER` (consumption, voting).

---

## 4. Real-time WebSocket Architecture

The backend wraps an HTTP server and binds a native WebSocket server (`ws`):
- Connection lifecycle handles initial handshake, connection pool tracking, and ping/pong keep-alives.
- Event structure uses typed envelopes:
  - `STOCK_UPDATED`: Broadcast when stock is restocked or consumed.
  - `VOTE_UPDATED`: Broadcast when votes change.
- Broadcasting implementation will be wired to business services during Phase 2.
